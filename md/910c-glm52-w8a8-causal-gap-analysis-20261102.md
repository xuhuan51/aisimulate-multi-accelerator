# 910C / GLM-5.2 W8A8：剥离残差后的缺口定位与修复

更新时间：2026-11-03。此文记录因果排查进展，不代表预测精度已经验收通过。

## 当前结论

此前两节点、四节点对照表使用了特定配置下拟合的整轮 forward 残差。那张表能说明历史校准版本对那些请求的重放结果，但不能证明算子模型本身准确，更不能据此保证新 workload、并发或并行方式的泛化效果。原始实测值和历史预测快照都保留；本文的排查不重新拟合整轮残差，也不把 profiler 引入的耗时当成真实推理成本。

关闭整轮残差后，TP16 / attention-DP4 / EP16 的低并发 eager decode 仍有明显低估。以下是同一轮真实 forward、四个 DP rank 完整配对后的中位数，单位均为 ms；这里的数值是设备事件 forward 耗时，不是端到端 TTFT。

因此，默认的独立算子相加模型仍低估约 50%。实际层调用链库已扩展为 240 个合格采样点；新增 12 组未参与建表的 8K 并发分布，稳态 decode MAPE 为约 2%～16%。最新完整 8K/1K 的 C1/C4/C8 独立请求模拟，TPOT 误差为 +0.28%/+2.16%/+7.74%，吞吐误差绝对值均小于 7%；C4/C8 的 TTFT 仍低估约 30%，不能宣布精度目标已完成。后文分别保留 24、144、240 点版本及完整请求结果，不修改历史原始数据、不使用旧残差。

## 2026-11-03：补齐混合 DP，并把剩余 prefill 缺口定位到 MoE

本轮新增了跨 DP 的 prefill/decode 混合轮次支持，完成 28 组短请求诊断，并用已有完整 8K/1K 请求的实际入口时间重新做了原生调度预测。没有修改旧实测，没有新增整轮残差，也没有修改已经发布的算子 parquet。精度目标尚未完成，特别是多 DP prefill 的 MoE 和两节点、四节点 PD 仍需要继续验证。

### 源码修复

实际容器内的源码重新从固定摘要 `sha256:5f384cab0e16a4951ed0bdc54e1280f2108aeda6b8ede90ee527d8f4b5146443` 提取。历史 `runtime-audit-20261029/latest` 缓存与该镜像部分文件不同，本轮使用镜像内的源码 SHA 校验，不依据目录名推断版本。

此前 `GroupShape` 只接受全组纯 prefill 或纯 decode。实际 8K/1K 记录中却出现 `[decode, prefill, prefill, decode]`，以及 `[prefill, decode, prefill, prefill]`。现已对齐以下规则：

- 每个 DP 保留本地注意力的阶段、query 长度和 KV 长度。
- 全组只要含 prefill，就使用 eager `SUM_LEN` padding；decode rank 也走全局 `normal` DeepEP 和 prefill 专家计算路径。
- 纯 decode 的真实层曲线只用于它所测量的路径。混合轮次展开其保留的独立算子列表，按上述通信规则计算，并明确标记 `estimated`。
- 混合轮次需要 `shape_policy: anchored`；`measured` 不将未采集的混合边界当作已测数据。同一个 DP 内的混合 chunk 仍不支持，与此次实测关闭 mixed chunking 的配置一致。
- 增加规范模型接口 `estimate_ascend_dp_operations(rank_metrics)`，返回同一次 Rust 查询所选关键 rank 的算子分解；分解合计与 forward 查询一致。

修改集中在 `crates/core/src/perfmodel/engine/ascend_dp.rs`、`runtime.rs`、`crates/core/src/perfmodel/py.rs` 及 Python 薄接口。当前验证镜像为 `aisimulate-910c:mixed-round-repair-20261103-r2`，镜像 ID 为 `sha256:9f8b7b90c438b10daa203fadb3beebc537e61c722019915265aa002d7738c6c9`。

## 已经落实的修复

1. **补齐 CPU 到 NPU 的长度元数据拷贝。** 真实 DCP=1 eager 路径每轮有 78 次注意力边界、21 次 indexer 刷新边界，把 CPU 上未锁页的 INT32 长度数组送到 NPU。此前注意力采集器预先准备了设备数组，遗漏了这段实际调用。现在增加 `seq_lens_h2d` 实测曲线，覆盖长度数组元素数 1、2、3、4、8、16、24、32，按真实 padding 后的 shape 查询；prefill 使用请求数，不把输入 token 总数误当成数组长度。主数据和另一个 device 的留出测量分别保留，发布继续执行原有完整性、数值正确性和 CV 门槛。
2. **拒绝继续叠加不兼容的旧残差。** 算子组成改变后，原先针对旧模型拟合的 residual 不能直接复用。显式残差配置增加算子合同版本检查；缺失或不匹配时给出错误。默认仍不添加整轮残差，旧报告使用固定的旧镜像保留复现能力；不能通过手工改版本标签把旧拟合值变成新证据。
3. **对齐 PD 的 KV 页延迟回收顺序。** 对照目标镜像真实 allocator 的 CPU 行为，修复已释放页、尚未使用页和延迟整理之间的分配顺序，并覆盖失败分配后的合并行为。此修复属于调度和 KV 状态对齐，不声称它解释了稳定 decode 的约 200 ms 缺口，也没有凭空加入“冷编译耗时”。

长度数组元素数为 4 时，主测量每次约 0.037616 ms，99 次调用增加约 3.724 ms。这个增量来自对应操作的独立实测和源码调用次数，不是对端到端误差拟合的补偿。

## 新证据把排查重点移到了哪里

先前只看 TTFT/TPOT，无法区分排队和执行。现在已经沿真实请求、forward iteration、DP rank、模块调用、CPU/NPU 时间线逐级核对：线性调用数、78 层注意力、75 层 MoE、21 次 indexer 刷新及主要集合通信调用数没有出现“漏了一半层数”这类错误。

早期独立线性算子探针测试了 `[4,2112,6144]`、`[4,18432,1536]`、`[4,6144,4096]`，其中三维依次为 M/N/K。需要纠正：前两个是通用控制 shape，不是本模型对应投影的真实尺寸。随后读取实际 config 的 `q_lora_rank=2048` 等字段，在 25 节点补测了真实 `[4,2624,6144]`、`[4,4096,2048]`、`[4,6144,4096]`。16 rank 同时运行、及时释放输出时，各 rank 中位数的中位数分别约 0.0745、0.0743、0.0736 ms，最慢 rank 约 0.0831、0.0840、0.0825 ms。所有数值检查通过，支持“线性内核本身没有普遍翻倍”，不能单独证明全部算子均准确。此前普通 `nn.Module` 边界也没有产生足以解释整轮缺口的增量；逐次强制同步会增大成本，但真实程序并非每个 GEMM 都同步，不能无条件替换成较慢值。

16 个 rank 的两轮 CPU/NPU profiler 时间线进一步显示：矩阵计算和稀疏注意力内核本身没有普遍扩大到原来几倍；DeepEP dispatch 的设备区间包含明显的跨 rank 等待，长度元数据的阻塞拷贝也会暴露前序工作尚未完成的等待。同一次采集中，rank0 的 dispatch 内核区间合计约 267 ms/轮，rank5 约 57 ms/轮，而它们最终完成的是同一轮分布式计算。这不能解释为两块卡网络带宽相差数倍，更不能把最长等待再加到其他 rank 的耗时上。

需要特别区分以下边界：

| 数据 | 实际包含什么 | 可以怎样使用 |
| --- | --- | --- |
| 独立 eager 算子事件耗时 | 对应调用链的提交、设备执行，以及测量流中出现的空档 | 当前算子表查询；不能再无条件叠加同一段 CPU 时间 |
| CPU 主线程时间 | Python/C++/驱动执行，也可能包含轮询 | 定位主机执行成本；不是纯 Python 开销 |
| DeepEP 内核持续时间 | 通信、量化/路由相关工作以及等待其他 rank | 分析分布式依赖和到达时序；不是纯数据传输时间 |
| 阻塞 H2D 调用的 wall time | 拷贝及其同步所等待的前序工作 | 分析同步边界；不能按“每次完整等待时间 × 次数”重复收费 |
| 未被计算/通信内核覆盖的设备时间 | DMA、事件、流空闲等 | 帮助定位；不能全部命名为调度开销 |

完整 profiler 将原本约 400～420 ms 的轮次增加到约 580～596 ms；原生栈采样也造成了明显扰动。因此时间线只用于定位调用与等待关系，其绝对耗时没有写入性能数据库，没有拿来生成新的固定残差。

**目前证据优先指向：独立算子采集与真实 eager 调用链之间的主机提交成本、同步边界和跨 rank 到达时序差异。** 仍需用真实模块隔离回放、同 shape 同边界的对照进一步拆分，不能在因果链尚未闭合时声称已经找到唯一原因。

## 当前仍在进行的工作

已经完成一组真实模块隔离回放：复用驻留权重，捕获真实注意力、MoE 和 decoder layer 的输入及残差状态，再用同样的模块和通信组回放。输入克隆、控制同步放在测量区间外，16 个 rank 的 6 个边界均完成了 3 次预热、9 次计时，并逐次通过输出数值校验。这是为了判断“同样的算子组合成真实层后增加了什么”，不是拟合整轮误差。首次诊断错误地启用了额外 HCCL 控制通信，导致额外显存申请失败；失败日志保留，改用服务既有 Gloo 组后成功。

在 indexer 复用的第 4 层，rank0 的隔离事件中位数为：注意力模块 1.871 ms、MoE 模块 1.841 ms、完整 decoder layer 4.839 ms。第 3 层是从 dense 到 MoE 的特殊入口，其完整层为 5.091 ms。两层不能不加区别地乘以全部层数。该实验已经说明差异发生在层内真实执行边界，不能只归因于 HTTP、PD 路由或 scheduler 排队。还需继续分解调用链，不能直接拿“完整层减去旧预测”当成补偿项。

25 节点也完成了相同线性算子的单 worker / 16 worker 并发对照。多数 shape 的中位数仍接近单 worker 数据，但最慢 rank 会更慢，首次 shape 还存在明显波动。因此后续需要保留各 rank 的分布与同步关系，不能只将某个孤立 device 的最佳耗时外推到全部 rank。

另外采集了独立于计时样本的 cProfile 调用图。第 4 层注意力、MoE、完整层分别记录 929、1279、2768 次 Python/C 调用，分布于量化矩阵乘、Triton、张量操作、集合通信和流/事件管理。该数据帮助定位真实调用边界；cProfile 本身增加了耗时，其绝对时间没有写入算子库。当前尚未找到一个单独调用可以解释全部差异。

只有明确一项实际缺失的调用、输入布局差异或依赖关系，才修改采集器/组合逻辑；再在其他输入长度、并发和并行方式上验证。当前不把上述 profiler 区间直接转换成残差曲线。

### TTFT 需要继续分开的因素

同一批配对遥测中的纯 prefill，4096 token/rank、1 个活跃 DP 时实测中位数约 1434.8 ms，原算子预测约 1420.0 ms，逐轮 MAPE 约 1.8%；4 个活跃 DP 时约为 1893.5 ms 对 1549.7 ms，逐轮 MAPE 约 17.5%。这说明 decode 的调用链修复不能直接代表 prefill 也已对齐。预热和服务初始化必须与正式请求分开查看，分析脚本另外保留了按 benchmark 时间窗口过滤的版本。

此外，已记录的真实 PD 请求中，首次分配 KV 时约 2.1 秒的额外等待主要发生在 Triton compile API 内；不同 free-pages 视图的 16 字节对齐会产生不同特化，同一编译 API 调用也可能只是在加载缓存。此处需要按真实缓存状态和特化身份建模，不能每个 rank 固定加 2.1 秒。客户端 TTFT 还可能从第一个非空文本块开始计算，而计算模型通常从第一个输出 token 开始计算。当前没有把这两类差异塞回整轮残差，所以完整请求 TTFT 的精度目标仍未完成。
